## BUG-WC-001 — client `woocommerce` no puede leer GET /products/{id}/stock (403)

**Severidad**: ALTA (stock WC → TPV roto silenciosamente)

**Cómo se reproduce**:
1. Crear producto en WC con `_manage_stock=yes`, `_stock=10`.
2. Cambiar `_stock` a 55 vía `$product->set_stock_quantity(55); $product->save()`.
3. El hook `woocommerce_product_object_updated_props` llama a `push_wc_stock_change()`.
4. Este hace `GET /products/{tpvId}/stock` para calcular delta → **403 HTTP**.
5. Se encola en `wp_tpv_sync_queue` con `operation='stock.push', absolute_target=55`.
6. Al procesar la queue, se vuelve a llamar al GET que sigue devolviendo 403 → backoff → abandonado.

**Logs confirman**:
```
GET /products/108799/stock → 403: HTTP 403
push_wc_stock_change: no se pudo leer stock TPV — encolando para reintento
```

**Fixes posibles**:
- **Recomendado**: en el TPV, dar al client_id="woocommerce" el scope `stock:read` (o el equivalente) para `/products/{id}/stock`.
- Alternativo: en `class-product-sync.php::push_wc_stock_change()`, usar GET /products/{id} y leer `$body.quantity` (que sí funciona para este cliente).
- Alternativo: usar PATCH `/products/{id}/stock` con un `set_quantity_absolute` (si la API lo expone) en lugar de `quantity_change` delta.

**Impacto**: cualquier ajuste manual de stock (stocking back-office en WC) nunca se propaga al TPV. En producción el cliente ve stock desfasado.

**Archivos**: `includes/class-product-sync.php:432-458`

## BUG-WC-002 — PATCH /products/{id} con `quantity` no aplica en updates

**Severidad**: MEDIA

**Cómo se reproduce**:
1. Crear producto en WC con qty=10 → TPV lo guarda correctamente (10).
2. Cambiar `_stock=55` en BD WC.
3. Llamar `push_wc_product_to_tpv()` (force_push) → envía PATCH con `quantity: 55` en el payload.
4. GET /products/{id} devuelve `quantity: 10` (no se aplicó).

**Fix**: en `class-product-sync.php:815`, eliminar `$payload['quantity']` de la rama PATCH (cuando existe tpv_id). Delegar stock exclusivamente al endpoint `/stock`.

**Archivos**: `includes/class-product-sync.php:815`

## BUG-WC-003 — Idempotency webhook NO atómica (race condition)

**Severidad**: MEDIA (agravada si TPV reintenta webhooks)

**Cómo se reproduce**:
```bash
# Enviar 5 webhooks idénticos en paralelo
for i in 1..5; do
    send_webhook_raw "{\"event_type\":\"stock.adjusted\",...,\"idempotency_key\":\"SAME-KEY\"}" &
done
wait
```
Resultado observado: **2-3 procesados como nuevos** (esperado: 1).

**Raíz** (`class-webhook-handler.php:90-104`):
```php
$seen = get_transient('tpv_sync_idem_' . $idemKey);
if ($seen) { return 200 duplicate; }
set_transient('tpv_sync_idem_' . $idemKey, 1, DAY_IN_SECONDS);
```
El check-then-set **no es atómico**. Bajo carga el mismo webhook duplicado entra dos veces antes del set.

**Fix**: usar `add_option` que falla atómicamente si la clave existe, o una tabla dedicada con PK UNIQUE + `INSERT IGNORE`:
```php
$inserted = $wpdb->query($wpdb->prepare(
    "INSERT IGNORE INTO {$wpdb->prefix}tpv_sync_webhook_idem (idempotency_key, created_at) VALUES (%s, NOW())",
    $idemKey
));
if (!$inserted) { return 200 duplicate; }
```

**Impacto**: si el TPV dispara el mismo stock.adjusted 3 veces por reintentos (timeout 10s), el stock WC puede aplicarse 2 veces. Si el webhook es idempotente de verdad (stock absoluto) el daño es 0, pero si fuera delta, sería duplicado.

**Archivos**: `includes/class-webhook-handler.php:88-104`

## BUG-WC-005 — Circuit breaker queda open de forma residual

**Severidad**: BAJA

**Cómo se reproduce**: tras ejecutar toda la suite (muchas llamadas API), breaker_status puede estar `open` aunque el último reset fuera al principio.

## BUG-WC-006 — HPOS: `_tpv_status_origin` no se persiste con `update_post_meta`

**Severidad**: **CRÍTICA**. Causa **bucle TPV↔WC** cuando un cambio de estado originado en TPV desencadena el hook de WC que lo reenvía al TPV.

**Cómo se reproduce**:
1. WC tiene HPOS activo (tablas `wp_wc_orders`, `wp_wc_orders_meta`).
2. Webhook `order.status_changed` llega → `update_wc_status($tpvOrderId, $tpvStatusId)`.
3. Línea 328 (`class-order-sync.php`): `update_post_meta($wcOrderId, '_tpv_status_origin', 'tpv');`
4. Con HPOS, `wp_postmeta` no es la fuente de verdad → la meta NO persiste en `wp_wc_orders_meta`.
5. `$order->update_status($wcStatus, ...)` dispara `woocommerce_order_status_changed` → `on_wc_status_changed()`.
6. En `on_wc_status_changed`, se lee `get_post_meta($wcOrderId, '_tpv_status_origin', true)` → **vacío** → se envía PATCH /orders/{tpv}/status al TPV.
7. El TPV actualiza, dispara webhook otra vez → bucle.

**Fix** en `class-order-sync.php::update_wc_status()`:
```php
// ANTES (línea 328):
update_post_meta($wcOrderId, '_tpv_status_origin', 'tpv');
$order->update_status($wcStatus, '...');

// DESPUÉS:
$order->update_meta_data('_tpv_status_origin', 'tpv');
$order->save();
$order->update_status($wcStatus, '...');
```

**Y en `on_wc_status_changed()`** (misma clase) al leer la meta — cambiar `get_post_meta()` por `$order->get_meta('_tpv_status_origin')`.

**Impacto**: en producción con HPOS, cada cambio de estado de orden originado en TPV se duplica entre TPV y WC. Sin llegar al infinito (el TPV a veces devuelve "ya está en ese estado" como no-op), pero sí genera PATCH innecesarios y posibles estados inconsistentes.

**Archivos**: `includes/class-order-sync.php:203-233` (on_wc_status_changed) y `class-order-sync.php:328` (update_wc_status).
